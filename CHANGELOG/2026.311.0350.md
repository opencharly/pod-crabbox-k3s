# 2026.311.0350 — docs(bed): the engine selector is no longer a toolchain limit

Corrects a claim in the bed header that is no longer true, so the next reader does not go looking for a bug that has been fixed.

## Summary

`charly.yml`'s header said, as a fact about the toolchain, that a `pod:` deploy's authored `engine:` selector is dropped by the check-bed `config`/`start` path and that `charly deploy add --engine` is an unknown flag, citing `opencharly/charly#1109`.

Both are false now:

- `charly#1109` is **CLOSED**, and `charly#1110` (merge `f24b0fda3069347eb45da2b304cd16c2b6d2f5f6`, tag `v2026.309.2052`) landed the fix — the selector is persisted into the per-host deploy entry and the emitted unit carries the selected engine's argv.
- `charly deploy add --engine=<word>` exists on the pinned binary `2026.310.0325`.

So this bed not claiming the containerd substrate is a **scope choice, not a limit it is working around**. A containerd venue still needs a `crun` runtime handler on the host — a separate prerequisite, and the reason the sibling `pod-crabbox-k3s-krun` bed could not be proven on this host (`opencharly/pod-crabbox-k3s-krun#2`).

Comment only. No behaviour, no assertions, no steps change.
